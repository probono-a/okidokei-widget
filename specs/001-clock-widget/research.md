# Phase 0 Research: 常駐デスクトップ時計ウィジェット

**Feature**: `001-clock-widget` | **Date**: 2026-09-17

技術選定のうち、仕様書 (`spec.md`) や要件定義 (`docs/requirements.md`) では明示されておらず、
実装前に決めておく必要がある事項を整理する。

## 1. .NET バージョン

- **Decision**: .NET 10 (LTS) + C# 最新言語バージョン、`net10.0-windows` をターゲットとする
- **Rationale**: 新規プロジェクトであり、本セッション時点(2026-09-17)で最新の LTS が .NET 10
  (2025-11 リリース)であるため、サポート期間を最大化できる
- **Alternatives considered**: .NET 8 (旧 LTS、2026-11 でサポート終了予定のため新規採用は不利)

## 2. マルチモニタ列挙とモニタ識別

- **Decision**: `System.Windows.Forms.Screen`(WPF アプリから WindowsDesktop SDK 経由で参照可能)
  でモニタの列挙・作業領域取得を行う。ただし永続化する「モニタ識別子」には
  `EnumDisplayDevices`(P/Invoke)で取得できる EDID 由来のデバイス ID を使う
- **Rationale**: `Screen.DeviceName`(`\\.\DISPLAY1` 等)はケーブル挿し直しや接続順序の変化で
  同じ物理モニタに対しても変わり得る。EDID 由来の ID は物理モニタに紐づき、再接続後も安定する
  ため、Edge Case「モニタ取り外し時も設定を保持し、再接続時に復元する」(FR-014, FR-015, SC-005)
  を満たすために必要
- **Alternatives considered**: `Screen.DeviceName` をそのままキーにする案(実装は単純だが、
  再接続順序によって設定が別モニタのものとして扱われ SC-005 を満たせないため却下)
- **訂正 (2026-09-28、issue #52)**: 上の Rationale の「EDID 由来の ID は物理モニタに紐づき、
  再接続後も安定する」は誤りだった。EDID 由来なのは ID のうちメーカー・型番の部分だけで、残りは
  つないでいる出力先 (端子) ごとの値だった。モニタの見分け方は #20 で決め直した

## 3. 自動起動の実装方式

- **Decision**: スタートアップフォルダ(`shell:startup`)へのショートカット (`.lnk`) 作成/削除
  で自動起動の ON/OFF を実装する。レジストリの Run キーは使用しない
- **Rationale**: Constitution Core Principle III(設定はレジストリを使わない)の趣旨を自動起動の
  実装方式にも一貫して適用する。ショートカットの作成/削除は ON/OFF 切替の実装として十分に単純
- **Alternatives considered**: レジストリ Run キー(Constitution の Additional Constraints で
  許容されてはいるが、レジストリ不使用の原則をアプリ全体で一貫させるため今回は不採用)

## 4. アプリの識別名・設定ファイルの保存場所

- **Decision**: アプリの識別名(≒設定フォルダ名)を `OkidokeiWidget` とし、設定ファイルは
  `%APPDATA%\OkidokeiWidget\settings.json` に保存する。`Okidokei` は「置き時計」に由来する
  造語
- **Rationale**: `docs/requirements.md` に記載の想定 (`%APPDATA%` 配下) に従う。ユーザー単位で
  書き込み権限が確実にあり、管理者権限を必要としない。`ClockWidget`・`DesktopClockWidget`
  はいずれも一般的すぎて他アプリと衝突する可能性があるとの指摘を受け、日本語由来の造語による
  独自性の高い名称に変更した
- **Alternatives considered**:
  - 実行ファイルと同じフォルダ(`Program Files` 配下等に配置されると書き込み権限が無い場合が
    あるため不採用)
  - `%APPDATA%\ClockWidget` のような単独フォルダ名(汎用的すぎて他アプリと衝突するリスクが
    あるため不採用)
  - `%APPDATA%\<作者名>\ClockWidget` のようなベンダー名フォルダを挟む案(Windows では一般的
    な構成だが、開発者の実名がアプリ内部のパスに恒久的に埋め込まれてしまうため不採用)
  - `%APPDATA%\DesktopClockWidget`(リポジトリ名由来だが、依然として説明的すぎて一般名詞に近く、
    人間からより独自性のある名称が欲しいとの要望を受けて `OkidokeiWidget` に変更した)

## 5. High DPI 対応

- **Decision**: アプリマニフェストで Per-Monitor V2 DPI 認識を宣言する
- **Rationale**: Constitution Core Principle V(マルチモニタ・DPI 対応)を満たすため。.NET の
  WPF は Per-Monitor V2 宣言時、モニタ間移動時の DPI 変化に自動追随する
- **Alternatives considered**: System DPI Aware(モニタ間で DPI が異なる構成でウィジェットの
  文字サイズ・位置が崩れるため不採用)
- **追記 (2026-09-24)**: 「WPF が DPI 変化に自動追随する」だけでは、WPF が Windows の提案する
  位置へウィンドウを動かしたまま、保存済みの位置へ戻さない (issue #25)。DPI だけの変更では
  `WM_DISPLAYCHANGE` が届かず、アプリ側の再配置が走らないため。`Window.DpiChanged` で保存済みの
  位置から配置し直す対応を追加済み。アンカー指定 (#15) の再配置もこの経路に乗せる
- **計測時の注意 (2026-09-24)**: 外部のスクリプトからウィンドウやモニタの座標を測るときは、
  スクリプト側も Per-Monitor V2 (`SetThreadDpiAwarenessContext(-4)`) にすること。システム DPI
  対応のままだと、拡大率が異なるモニタの座標が換算された値で返り、誤った結論を導く
  (issue #25 の調査で実際に起きた。issue #25 の訂正コメントを参照)

## 6. 二重起動防止

- **Decision**: 名前付き Mutex による多重起動チェック。2 つ目のプロセスは何もせず終了する
- **Rationale**: Edge Case「二重起動時は既存ウィジェットにフォーカス、または何もしない」に対し、
  Assumptions で「詳細な排他制御の方式は実装時に妥当な標準的手法を選定してよい」とされており、
  最小実装で要件を満たせる
- **Alternatives considered**: 既存プロセスへフォーカスを移す IPC 実装(個人用ツールとしては
  過剰なため、YAGNI により不採用。「何もしない」で仕様を満たす)

## 7. テスト方針

- **Decision**: 見た目に依存しないロジック(設定の読み書き・デフォルトへのフォールバック・
  モニタ識別子のマッチング)は xUnit による単体テストで検証する。UI・視覚的な確認は
  `quickstart.md` の手動シナリオで行い、UI 自動化フレームワークは導入しない
- **Rationale**: Constitution Core Principle I(シンプルさ優先)に従い、個人用ツールに UI
  自動化テストの導入コストを払わない。一方で FR-018(壊れた設定ファイルでもクラッシュしない)
  等は自動テストで継続的に保証する価値があるため単体テストは行う
- **Alternatives considered**: WPF UI 自動化(FlaUI 等)の導入(個人用ツールの規模に対して
  過剰なため不採用)

## 8. クイック切替 UI の実装形態

- **Decision**: 常駐トレイアイコンを追加せず、ウィジェット本体への右クリックで表示する
  `ContextMenu` として実装する
- **Rationale**: `docs/requirements.md`・`spec.md` とも「右クリックメニュー」とのみ記載しており
  トレイアイコンは要求されていない。トレイアイコン実装には追加ライブラリ
  (`Hardcodet.NotifyIcon.Wpf` 等)が必要になり、Core Principle I(YAGNI)に反する
- **Alternatives considered**: システムトレイアイコン + メニュー(要求されていない機能であり
  依存関係も増えるため不採用)
- **追記 (2026-09-24)**: 右クリックメニューをウィジェット本体に実装する方針は維持する。ただし
  タスクトレイの右クリックメニューにも同じ項目を持たせることになった (FR-038)。詳細は #17

## 9. 最前面表示の限界

- **Decision**: WPF 標準の `Topmost` プロパティで実装する。DirectX 排他フルスクリーンモードの
  ゲーム等、OS レベルで最前面表示を上書きするアプリケーションについては対応範囲外の既知の制約
  として扱う
- **Rationale**: Edge Case で言及されている「フルスクリーンアプリ上でも表示され続ける」ことへの
  期待は、ウィンドウモード/ボーダレスウィンドウのアプリに対しては `Topmost` で満たせる。
  排他フルスクリーンは OS の描画パイプラインを専有するため、追加のフック等での回避は個人用
  ツールの範囲を超える(YAGNI)
- **Alternatives considered**: 定期的に `Topmost` を再設定し続けるポーリング(効果が限定的な
  上、Core Principle II の軽量常駐に反するため不採用)

## 10. サードパーティ (OSS) ライブラリのライセンス確認方針

- **Decision**: 本体 (`OkidokeiWidget.Core` / `OkidokeiWidget.App`) が選定した依存関係は
  BCL・WPF・`System.Windows.Forms`(いずれも .NET SDK/ランタイムに含まれ、追加の NuGet
  パッケージ取得を要しない)のみである。一方、テストプロジェクト
  (`OkidokeiWidget.Core.Tests`) は xUnit 関連パッケージ (`xunit`, `xunit.runner.visualstudio`,
  `Microsoft.NET.Test.Sdk`) という外部 NuGet パッケージに依存するため、これらは導入前に必ず
  ライセンス(MIT 等の許諾条件、コピーレフト条項の有無、表示義務等)を確認し、個人利用の範囲で
  問題ないことを確かめてから採用する (tasks.md T004)。今後さらに他の外部 NuGet パッケージの
  導入が必要になった場合も、同様に導入前の確認を必須とする
- **Rationale**: 人間から明示的に「OSS 等を使う場合はライセンスの確認をすること」との指示が
  あったため。本体コードには現行の技術選定 (research.md #1, #2, #6, #8) で外部 OSS 依存は
  発生していないが、テストランナーである xUnit は現時点で唯一該当する外部依存であり、
  確認済みの上で導入する
- **Alternatives considered**: テストランナーを使わず手動検証のみで済ませる案(FR-018 等の
  ロジックは自動テストで継続的に保証する価値があるため不採用。research.md #7 参照)

## 11. UI の見た目 (Windows 11 らしさ)

- **Decision**: `OkidokeiWidget.App` の `App.xaml` に `ThemeMode="System"` を設定し、
  .NET 9 で WPF に追加された標準の Fluent テーマ (`PresentationFramework.Fluent`、
  .NET SDK/ランタイム同梱、追加の NuGet パッケージ不要) を適用する
- **Rationale**: 実装後の実機確認で人間から「設定ダイアログが古臭い」「Windows 11 っぽくない」
  との指摘を受けた。原因はフォントではなく、WPF の既定コントロールテンプレート(角丸なし・
  クラシックな見た目)であった。人間から「OSS じゃなくて Windows 標準の新しいライブラリって
  ないの?」との要望があり、.NET 9 以降 WPF 本体に組み込まれている公式の Fluent テーマ機能
  (`Application.ThemeMode`)がこれに合致するため採用した
- **Alternatives considered**:
  - `WPF-UI`(lepoco/wpfui)等の OSS 製 Fluent 系 WPF UI ライブラリの導入(機能は豊富だが、
    人間の要望により OSS への新規依存を避けるため不採用)
  - 既定コントロールの `ControlTemplate` を自前で XAML 化して角丸・フラット化する案
    (依存追加は不要だが、公式の Fluent テーマがそのまま使える以上、車輪の再発明になるため不採用)
- **文字色選択 UI**: `System.Windows.Forms.ColorDialog`(Windows 2000 時代から見た目が変わって
  いない共通ダイアログ)は Fluent テーマの対象外だったため、`OkidokeiWidget.App` に自作の
  `ColorPickerWindow`(パレット + `#RRGGBB` 入力、WPF のみで実装)を追加して置き換えた。
  これにより `System.Windows.Forms`/`System.Drawing` への依存も不要になったため、
  `UseWindowsForms` を無効化し `ImplicitUsings` を再度有効化した
  - **Alternatives considered**: WinUI3 の `ColorPicker`(XAML Islands 経由での WPF 連携が必要で、
    個人用ツールの規模に対して過剰なため不採用)、`ColorDialog` を使い続ける案
    (見た目が古いままになるため不採用)
- **ダークモード時のタイトルバー**: `ThemeMode="System"` はウィンドウ内のコントロールの見た目
  はダーク/ライトに追従させるが、ウィンドウのタイトルバー(非クライアント領域)までは自動で
  追従しない。人間の実機(ダークモード設定)で「ダークモードに対応してない」との指摘を受け、
  タイトルバーだけ白いまま取り残されていたことが原因と判明した。DWM API
  (`DwmSetWindowAttribute` の `DWMWA_USE_IMMERSIVE_DARK_MODE`)をタイトルバーを持つ
  ウィンドウ (`SettingsWindow`, `ColorPickerWindow`) に個別適用し、レジストリ
  (`HKCU\...\Themes\Personalize\AppsUseLightTheme`) からシステムのダーク/ライト設定を読み取って
  切り替える `WindowThemeHelper` を追加した(`ClockWindow` はタイトルバー自体を持たないため対象外)
- **ダークモード時の文字が読めない不具合**: `SettingsWindow.xaml` の `Window.Resources` に
  `GroupBox`/`TextBlock`/`CheckBox`/`ComboBox`/`Slider` の暗黙スタイル(`x:Key` なし、
  余白調整のみが目的)を `BasedOn` 指定なしで定義していたため、Fluent テーマがそれぞれの型に
  対して用意しているダーク/ライト対応の既定スタイル(文字色・背景色を含む)を丸ごと上書きして
  しまい、チェックボックス横のラベルが黒文字のまま・コンボボックスのドロップダウン項目が
  白文字のままになり、ダークモードで読めなくなっていた。各スタイルに
  `BasedOn="{StaticResource {x:Type ...}}"` を追加し、Fluent テーマの既定スタイルへ差分を
  積み増す形に修正して解消した(WPF で暗黙スタイルを部分的に上書きする際の定石)

## 12. 詳細設定画面のレイアウト(タブ化)

- **Decision**: `SettingsWindow` を `TabControl` で「表示」「フォント」「レイアウト・背景」の
  3 タブに再編する。今後 US3(位置ロック・最前面表示)・US4(モニタ別表示・自動起動)で
  増える設定項目も、新規タブまたは既存タブへの追加として収める方針とする
- **Rationale**: Phase 9 で秒表示・時刻/日付それぞれのフォント設定・日付/曜日の表示形式等を
  追加した結果、詳細設定画面が単一のスクロールしない縦一列レイアウトのままでは縦に伸び続けて
  しまうと人間から指摘を受けた。個人用ツールであっても US3・US4 でさらに設定項目が増える
  ことが分かっているため、この時点でレイアウトの拡張性に対応しておく方が手戻りが少ない
- **Alternatives considered**:
  - `ScrollViewer` で縦スクロール可能にするだけの案(実装は最小限だが、設定項目が多いと
    どこに何があるか見渡しにくくなり、Windows 標準の設定アプリ的な体験からも外れるため不採用)
  - ウィンドウを横に広げて 2 カラムにする案(画面の狭い環境で扱いにくくなる懸念があるため不採用)
- **追記 (2026-10-01)**: 「モニター・起動」タブはなくした。表示/非表示は、選んだモニタの「表示」タブで切り替え、自動起動はタスクトレイの右クリックメニューに移した (#23・#24)

## 13. タスクトレイ常駐アイコン(最前面復帰用)

- **Decision**: タスクトレイに常駐アイコンを追加する。ただし #8 で決定した「右クリックメニューを
  ウィジェット本体に実装する」方針自体は変更せず、トレイアイコン側は「すべてのウィジェットを
  最前面に呼び戻す(クリック)」「終了(右クリックメニュー)」のみを提供する薄い実装とする。
  実装は `System.Windows.Forms.NotifyIcon` を使わず、`Shell_NotifyIcon`(shell32.dll)への
  P/Invoke + 非表示の `HwndSource` によるメッセージ受信で行う
- **Rationale**: 「最前面表示」を OFF にした状態でウィジェットが他のウィンドウの背後に完全に
  隠れると、`ShowInTaskbar="False"`(タスクバー非表示)の設計上、前面に戻す手段が一切ない
  ことが実機確認で判明した。#8 の「トレイアイコンを追加しない」という決定は、右クリックの
  クイック切替 UI 全体をトレイアイコン化することへの反対であり、この具体的な使い勝手の欠落は
  想定していなかったため、範囲を絞った上で再度決定し直した。`NotifyIcon`(WinForms)を使うと
  `UseWindowsForms` の再有効化が必要になり、以前(research.md #11)`ImplicitUsings` の
  WPF/WinForms 型名衝突を理由に切り離した経緯を再び持ち込んでしまう。`Shell_NotifyIcon` への
  直接 P/Invoke であれば追加の NuGet パッケージも `UseWindowsForms` も不要で、
  `OkidokeiWidget.Core` のモニタ列挙(`EnumDisplayMonitors` 等)と同様の「素の Win32 API」
  という一貫した方針を保てる
- **Alternatives considered**:
  - `System.Windows.Forms.NotifyIcon`(実装は簡単だが `UseWindowsForms` の再有効化が必要で
    `ImplicitUsings` 無効化+全ファイルへの明示 `using` 追加が再度必要になるため不採用)
  - `Hardcodet.NotifyIcon.Wpf` 等の OSS ライブラリ(#8 で不採用とした理由と同じく、要求されて
    いない機能への追加依存を避けるため不採用)
  - トレイアイコンを追加せず、代わりにウィジェットを `ShowInTaskbar="True"` にしてタスクバー
    経由で前面に戻す案(依存追加が不要な代替案として比較検討したが、人間からタスクトレイ
    常駐アイコンの方が希望として明示されたため、そちらを採用した)
- **追記 (2026-09-24)**: 「トレイ側は呼び戻しと終了のみの薄い実装」という範囲の限定は、
  FR-038 により撤回した。トレイの右クリックメニューはウィジェット本体と同じ項目を持つ (#17)。
  `Shell_NotifyIcon` への P/Invoke と非表示 `HwndSource` という実装方式は変更しない
- **追記 (2026-10-01)**: トレイの右クリックメニューは、FR-038 の改訂で「詳細設定...」「自動起動」「終了」だけにした (#24)。実装方式は変更しない

## 14. アプリケーションアイコン

- **Decision**: 時計をイメージした専用のアイコン(丸型の文字盤・針)を新規に作成し、
  `src/OkidokeiWidget.App/app.ico` として追加する。`OkidokeiWidget.App.csproj` の
  `ApplicationIcon` に指定して実行ファイルのアイコンとし、同じファイルを `ClockWindow`/
  `SettingsWindow` の `Icon` プロパティおよびタスクトレイアイコン(research.md #13、
  実行ファイル自身に埋め込まれたアイコンを実行時に抽出して使う)にも流用する
- **Rationale**: 人間から「アプリアイコンが欲しい(デザインは任せる)」との要望があった。
  既製のアイコン素材(OSS・フリー素材)を探して導入する案もあったが、ライセンス確認
  (research.md #10 の方針)の手間や配布条件の制約を避けるため、シンプルな図形のみで構成される
  アイコンを自作する方針とした
- **Alternatives considered**: フリー素材サイトのアイコンを利用する案(ライセンス確認の手間と、
  個人の思い通りのデザインにならない制約があるため、実装時に自作する方を選んだ)

## 15. アンカー指定の位置計算 (FR-034, FR-035, SC-007)

- **Decision**:
  - アンカーは 9 通りの位置 (`TopLeft`〜`BottomRight`) を 1 つの enum で表す。横と縦を別々の
    値として持つことはしない
  - 余白は DIP (WPF の論理単位) の固定値で定義する。「狭め」= 8 DIP、「広め」= 24 DIP
  - 配置のたびに、ウィンドウが乗っているモニタの DPI スケールを掛けて物理ピクセルに変換する
  - 位置は `WidgetPlacementCalculator` (Core) で、作業領域・ウィジェットの実サイズ (物理
    ピクセル)・余白から計算する。例えば「右」なら `作業領域の右端 - ウィジェット幅 - 余白`
  - 「中央」の軸では余白を使わない。計算結果は既存の処理と同じく作業領域内へ収める
  - ウィジェットのサイズが変わるたび (`SizeChanged`) に再配置する。フォントサイズ変更や
    日付/曜日表示の切り替えでサイズが変わっても、隅からの位置関係を保つため
  - DPI 変更時は、issue #25 で追加した `DpiChanged` の経路で再配置する
- **Rationale**:
  - DIP 固定値に DPI スケールを掛ければ、拡大率が変わっても見た目の余白は同じになる (FR-035)
  - 9 値の enum にすると、「横だけ選ばれていて縦が未設定」という中途半端な状態が生じない
  - ウィジェットの実サイズは既存の `ApplyPlacement` がすでに `GetWindowRect` で取得している
- **Alternatives considered**:
  - 余白を物理ピクセルの固定値にする案 (拡大率によって余白の見た目が変わるため不採用。
    FR-035 で明示的に避けたい挙動)
  - 余白をウィジェットの高さに対する比率にする案 (フォントサイズを変えると余白も変わって
    しまい、「狭め/広め」の見た目が一定にならないため不採用)
  - 横位置・縦位置を別々の enum で持つ案 (上記の中途半端な状態の扱いを決める必要が生じるため
    不採用)
- **調整余地**: 8 / 24 DIP という値は実機で見た目を確認して調整してよい。値の変更は
  `WidgetPlacementCalculator` 内の定数のみで完結させる
- **追記 (2026-09-24、implement 中の実機確認)**: 右クリックメニューで 9 つの配置を 1 列に並べたところ、
  「縦にずらずら並んで直感的に分かりにくい」との指摘があった。メニューは「横位置 ▶ 左/中央/右」
  「縦位置 ▶ 上/中央/下」と軸ごとに選ぶ形に変更した
  - 保存形式は 9 値の `Anchor` のまま変えない。メニューで選んだ軸と、もう片方の軸を組み合わせて
    9 値に変換する (`AnchorAxes`)
  - 当初 9 値にした理由の「横だけ決まっていて縦が未設定」という状態は、次の規則で作らない。
    アンカー指定中はもう片方の軸を今の値のまま使う。自由配置中は、もう片方の軸を今の位置から
    一番近いもの (作業領域を 3 等分し、ウィジェットの中心がある所) にする
  - 自由配置中にもう片方を常に「上」「左」にする案は、画面の下にあるウィジェットで「右」を
    選ぶと右上まで飛んでしまい驚きやすいため不採用とした

## 16. アンカー指定の保存形式と既存ユーザーの扱い (FR-034, FR-036)

- **Decision**:
  - `MonitorPlacement` に `Anchor` (null 許容の `AnchorPosition`) と `AnchorMargin`
    (`AnchorMargin` enum、既定値は `Narrow`) を追加する
  - `Anchor` が null なら自由配置 (既存の `X`/`Y` を使う)、値があればアンカー指定とする
  - アンカー指定中も `X`/`Y` は消さずに残す。ドラッグで自由配置に戻したときは、ドラッグ後の
    座標で上書きし、`Anchor` を null に戻す (FR-036)
  - `AnchorMargin` は自由配置中でも保持する。自由配置中に余白を選んだ場合は値を保存するだけで、
    ウィジェットは動かさない
- **Rationale**:
  - 既存の `settings.json` には `Anchor` がないため、読み込むと自動的に null (自由配置) になる。
    マイグレーション処理なしで「アップデートしても既存ユーザーの位置は変わらない」を満たせる
  - バージョン番号フィールドを持たないという既存方針 (contracts/settings-file.md) も維持できる
  - 余白を位置とは別に持つと、自由配置中でもメニュー上で余白のチェック状態を常に表示できる
- **Alternatives considered**:
  - 配置モード (`Free`/`Anchor`) を別フィールドで持つ案 (`Anchor` の null とモードの 2 つが
    食い違う状態があり得るため不採用)
  - アンカー指定時に `X`/`Y` を消す案 (保存形式が状態によって変わり、読み込み側の分岐が
    増えるため不採用)
- **追記 (2026-09-26、issue #43)**: 自由配置中の余白の扱いを見直した。詳細は #19 を参照
  - 自由配置中は、余白のチェックを表示しない (上の Rationale の「チェック状態を常に表示できる」は
    取りやめ)
  - 自由配置中に余白を選ぶと、値を保存するだけでなく、範囲内の縁から余白ぶん離す (上の Decision の
    「ウィジェットは動かさない」を置き換え)
  - `AnchorMargin` を自由配置中も保持する保存形式は変えない

## 17. 右クリックメニューの構成と共通化 (FR-010, FR-012, FR-037, FR-038)

- **Decision**:
  - 本体とタスクトレイの右クリックメニューは、どちらも以下の構成にする
    - 詳細設定...
    - 位置ロック / 最前面表示 (チェック付き)
    - 配置 ▶ (横位置 ▶ 3 項目、縦位置 ▶ 3 項目、余白 ▶ 2 項目。#15 の追記を参照)
    - 終了
  - タスクトレイでは「配置」の下にモニタの一覧を挟む。ラベルは詳細設定画面と同じ
    「モニター N (プライマリ)」形式にする
  - モニタの一覧には、ウィジェットを表示中のモニタのみを出す。非表示のモニタは右クリック
    できるウィジェットがないため、トレイからも対象外とする
  - 位置ロック中は「配置」の項目をグレーアウトする (FR-010)。無効にするのは末端の選択肢
    (左/中央/右、上/中央/下、狭め/広め) で、「配置」「横位置」「縦位置」「余白」やトレイの
    モニタ名は有効のままにする。WPF では
    無効な親のサブメニューは開けず、ロック中に今の配置を確認できなくなるため
    (`/speckit-analyze` の指摘 I1 で修正)
  - 「配置」のサブメニューを作る処理は `PlacementMenuBuilder` (App) に共通化し、本体と

  - 本体のメニューは、チェック状態やグレーアウトを最新にするため、開くたびに「配置」の
    サブメニューを作り直す。トレイのメニューは既存どおり開くたびに全体を作り直す
  - トレイのメニューの中身は `App` 側で組み立てる。`TrayIconManager` は右クリックを通知し、
    渡されたメニューを表示するだけにする
- **Rationale**:
  - 「配置」のサブメニューを 1 か所で作れば、本体とトレイで項目や表示が食い違わない
  - 位置ロック・最前面表示・詳細設定・終了は、すでに `App` のコールバックとして存在する。
    トレイからも同じコールバックを呼べば挙動も一致する
  - `TrayIconManager` に設定のことを知らせずに済み、Win32 の後始末だけを担当させられる
- **Alternatives considered**:
  - 本体のメニューを XAML のまま静的に定義し、開くたびにチェック状態だけ更新する案
    (9 項目 + 2 項目の状態更新を XAML とコードの両方に書くことになり、トレイ側との共通化も
    できないため不採用。区切り線など静的な部分は XAML に残してよい)
  - 本体のメニューもトレイと同じ階層にする案 (spec の Clarifications で不採用が決定済み)
- **追記 (2026-10-01)**: トレイのメニューから位置ロック・最前面表示・配置をなくしたため (FR-038 の改訂、#24)、本体とトレイを同じ構成に揃える決定と、トレイのモニタの階層は取り下げた。`PlacementMenuBuilder` は本体のメニューだけで使う

## 18. ドラッグで動かせる範囲の制限 (FR-009, FR-036, SC-008、2026-09-26 追加、issue #39)

- **Decision**:
  - ドラッグ中の位置は、WPF の `Left`/`Top` (DIP) ではなく、物理ピクセルで計算して
    `SetWindowPos` で動かす。自由配置の保存や `ApplyPlacement` と同じ単位にそろえる (issue #10)
  - ドラッグ開始時に、マウスの画面座標 (`GetCursorPos`) とウィンドウの左上 (`GetWindowRect`) の
    差を「つかんだ位置」として覚える
  - マウスが動くたびに `マウスの画面座標 - つかんだ位置` を求め、ウィジェットが表示されている
    モニタの作業領域内に収めてから動かす
  - 作業領域内へ収める計算は、`ApplyPlacement` がすでに使っている `WidgetPlacementCalculator`
    (Core) の処理を共通化して使う。自由配置・アンカー指定・ドラッグで同じ計算を通す
  - ドラッグ終了時の保存とアンカー指定の解除 (FR-036) は、今の処理のまま変えない。位置が
    変わったかどうかは見ない (spec.md の Clarifications)
- **Rationale**:
  - ウィンドウが作業領域から出なければ、Windows はウィンドウを別のモニタのものとみなさない。
    なので `DpiChanged` も、PR #42 で後回しにした再配置による引き戻しも起きない (issue #39 の
    コメントで推定した揺れの原因を、経路ごと断つ)
  - 今の実装の「前回からの移動量を `Left`/`Top` に足す」方式のまま端で止めると、止まっている間の
    移動量が捨てられ、つかんだ位置が少しずつずれていく。画面座標から毎回位置を求めれば、
    マウスを戻したときに、つかんだ位置に戻った所から再び動き出す (spec.md の Assumptions で
    実装時に決めるとした挙動)
  - `Left`/`Top` は DIP で、DIP と物理ピクセルの換算はウィンドウが乗っているモニタの拡大率で
    変わる。作業領域 (物理ピクセル) と比べる計算を DIP で行うと、issue #10 と同じずれを招く
- **Alternatives considered**:
  - `Left`/`Top` のまま、作業領域を DIP に換算して比べる案 (換算の基準になる拡大率がウィンドウの
    位置によって変わり、境界の付近で正しく換算できる保証がないため不採用)
  - ドラッグ中は `DpiChanged` による再配置を止める案 (境界をまたげること自体は残り、FR-009 の
    改訂内容を満たさないため不採用)
  - WPF の `DragMove()` を使う案 (移動中の位置に手を加えられず、作業領域内に収められないため
    不採用)

### 前提としている WPF / Win32 の挙動と確認結果 (constitution Development Workflow 7)

2026-09-26 に、最小の WPF アプリ (Per-Monitor V2、本体と同じ `app.manifest`) で確かめた。

- 確かめた方法
  - アプリ自身が `SendInput` でマウスを押し、100% のモニタ (プライマリ) の中央から、225% の
    モニタの中央へ向けて動かし、途中まで戻してから離す
  - `Border` の `CaptureMouse()` と `MouseMove` で、上の Decision と同じ計算でウィンドウを動かす
  - 作業領域内に収める `clamp` と、収めない `free` (対照実験) の 2 通りを、それぞれログに記録した
- 環境: モニタ 1 = 1920×1080 (100%、プライマリ)、モニタ 2 = 3840×2160 (225%、モニタ 1 の左)

| 前提 | 結果 | 根拠 (ログ) |
|---|---|---|
| Per-Monitor V2 では、`GetCursorPos` と `GetWindowRect` がどちらも物理ピクセルで、同じ座標系になる | 確認済み | 押した時点で、マウス (960,516) とウィンドウの左上 (910,496) の差が、置いた位置どおりの (50,20)。225% のモニタのマウス座標も (-3840〜0) の物理ピクセルで返った |
| ウィジェットを端で止め、マウスだけがウィンドウの外 (隣のモニタ) に出ても、キャプチャが続き `MouseMove` が届く | 確認済み | `clamp` で 167 回の `MouseMove` のうち 126 回がマウスがウィンドウの外にある状態で届き、離すまで `IsMouseCaptured` = true のままだった |
| ウィンドウが作業領域から出なければ、マウスが別の DPI のモニタへ出ても `DpiChanged` は起きない | 確認済み | `clamp` では `DpiChanged` が 1 回も起きず、拡大率は最後まで 1.0 のままだった。`free` では境界をまたいだ時点で `DpiChanged 1 -> 2.25` が起きた |
| 端で止まっている間にマウスを戻すと、つかんだ位置に戻った所から再び動き出す | 確認済み | 左端 (x = 0) で止まったまま、縦方向だけマウスに合わせて動き続けた。上端でも止まった後、マウスが上端より下に戻ると再び下へ動いた |

- 確かめていないこと (設計の前提にはしない)
  - ドラッグ中にモニタの拡大率や接続状態が変わる場合 (spec.md の Assumptions で範囲外とした)
- 確認用のアプリは scratchpad に置いた一時的なもので、リポジトリには含めない

## 19. 自由配置のときの余白 (FR-035, FR-039、2026-09-26 追加、issue #43)

- **Decision**:
  - 余白のチェックは、アンカー指定中だけ `AnchorMargin` の側に付ける。自由配置中はどちらにも
    付けない。`AnchorMargin` の値は今までどおり自由配置中も保持する (#16 の保存形式は変えない)
  - 自由配置中に余白を選んだときの移動先は、`WidgetPlacementCalculator` (Core) の 1 つの関数で
    求める。入力はウィジェットの今の位置とサイズ (物理ピクセル)・作業領域・余白・拡大率で、
    範囲内の縁がなければ「移動先なし」(null) を返す
    - 余白の物理ピクセルは、アンカー指定と同じ `余白 (DIP) × 拡大率` を四捨五入した値を使う
    - 横方向: 左の縁までの距離が余白以下なら `作業領域の左端 + 余白` へ、そうでなく右の縁までの
      距離が余白以下なら `作業領域の右端 - 幅 - 余白` へ動かす。どちらでもなければ動かさない
    - 縦方向も同じ (上、下の順に見る)。横と縦は別々に決めるので、隅の近くなら両方が動く
    - 最後に既存の `ClampToWorkArea` で作業領域内に収める
  - メニューのグレーアウトも同じ関数で決める。移動先が null の余白はグレーアウトし、それ以外は
    選べる。位置ロック中は今までどおりすべてグレーアウトする (FR-010)
  - 余白を選んだら、`AnchorMargin` を更新し、移動先を `X`/`Y` (作業領域の左上からの相対座標) に
    保存してから配置し直す。`Anchor` は null のまま (自由配置のまま)
  - グレーアウトの判定に使う位置とサイズは、メニューを開いた時点のウィンドウの位置
    (`GetWindowRect`) と拡大率 (`VisualTreeHelper.GetDpi`) を使う。横位置・縦位置を自由配置中に
    選ぶときと同じ取り方にする
- **Rationale**:
  - グレーアウトと移動を同じ関数で決めれば、「選べるのに動かない」「グレーアウトなのに本当は
    動ける」という食い違いが起きない
  - 余白の換算と四捨五入をアンカー指定とそろえれば、余白を入れた直後の縁までの距離がちょうど
    余白と同じになり、「余白以下なら選べる」(spec.md の Edge Cases) をそのまま満たす
  - 横と縦を独立に決めれば、「範囲内の縁が 2 つなら両方から離す」を特別扱いなしで満たせる
  - 位置の計算は Core にあるので、グレーアウトの境目 (距離 = 余白、余白 + 1 px など) を単体
    テストで押さえられる
- **Alternatives considered**:
  - グレーアウトの判定と移動を別々の関数で書く案 (条件が二重になり、食い違いの元になるため不採用)
  - 余白を選んだら `Anchor` を一時的に設定して `ToAnchoredPosition` を流用する案 (範囲内の縁が
    1 つだけのとき、もう片方の軸をどうするかを決められず、自由配置のままという spec の決定とも
    合わないため不採用)
- **補足**: 向かい合う縁が両方とも範囲内になる場合 (ウィジェットが作業領域とほぼ同じ大きさ) は
  spec で「定めない」とした (issue #45)。上の手順では左・上の縁が先に当てはまるが、これは
  仕様として保証する動きではない

## 20. モニタの見分け方と既存の設定の引き継ぎ (FR-040, SC-005、2026-09-28 追加、issue #52)

- **Decision**:
  - 設定ファイルに保存するキーの形は変えない。今までどおり、`EnumDisplayDevices` に
    `EDD_GET_DEVICE_INTERFACE_NAME` を指定して取得するデバイスインターフェース名
    (`\\?\DISPLAY#<型番>#<端子ごとの値>#{GUID}`) をそのままキーにする
    - `<型番>` はメーカーと型番 (例: `SNYAE04`・`DELF16C`)、`<端子ごとの値>` は出力先ごとの値
      (例: `5&3b7d6ecd&0&UID4352`)
  - `MonitorSettingsReconciler.Reconcile` で、次の順に設定を割り当てる
    1. 接続中のモニタのうち、キーが完全に一致する設定があるものは、それを使う (今までと同じ)
    2. 残ったモニタ (キーが一致しなかったもの) を型番ごとに分ける。型番ごとに、同じ型番の設定の
       うち「使われていない設定」(キーが接続中のどのモニタのキーとも一致しないもの) を集める。
       残ったモニタと使われていない設定を、それぞれキーの順 (文字列の順。`<端子ごとの値>` の番号順に
       ほぼ等しい) に並べ、先頭から 1 対 1 に組み合わせる。組み合わせた設定は、同じインスタンスの
       まま今のキーへ移し、古いキーを消す
       - 残ったモニタの中に同じキーのものが複数あっても、そのキーには 1 回だけ組み合わせる。2 つ目
         以降は 1 つ目と同じ設定を使う (未確認の前提 3 が外れて、同じ型番の 2 台が同じキーになった
         場合に、2 つ目の組み合わせが 1 つ目を上書きして設定を失わないようにするため。
         `/speckit-analyze` の 4 回目の指摘 H1)
    3. それでも組み合わせる設定がなかったモニタは、今までどおり新しいモニタとしてデフォルト値の
       設定を足す。組み合わせるモニタがなかった設定は、消さずに残す
  - `<型番>` は、キーを `#` で区切った 2 つ目の部分とする。区切った結果が 3 つ未満の場合と、2 つ目が
    空の場合は型番なしとし、1 の完全一致だけを使う (ID が取れず `\\.\DISPLAY1` のままのものなど)。
    キーの完全一致と同じく、大文字・小文字も区別して比べる (同じ Windows から取った ID どうしを
    比べるだけで、表記が揺れる理由がないため)
  - 2 の組み合わせ方は、人間の提案 (「同じ型番の設定が複数あれば、つないだ順に割り当てていく」) に
    よる。つないだ順は設定ファイルに記録していないため、今のキーから決められる端子の番号順にした
  - 付け替えた結果は、`Reconcile` の後の既存の `SettingsRepository.Save` でそのまま保存される
    (起動時・モニタ構成の変化時とも、`Reconcile` の後に保存している)
- **Rationale**:
  - spec で決めた動きは、どれもこの 3 段の規則で満たせる。場合ごとの特別な処理は要らない
    - 型番の違うモニタを別の端子につなぎ直した: 1 は外れ、2 で前の設定が移される
    - 型番の違うモニタ 2 台の端子を入れ替えた: どちらも 2 で、それぞれの型番の設定が移される
    - 同じ型番が 2 台つながっている: 端子ごとにキーが違うので、1 で端子ごとの設定が使われる
    - 同じ型番の 2 台を、レイアウトの変更や引越しで別の端子につなぎ直した: 2 で、2 つの設定が
      端子の番号順に 1 つずつ割り当てられる。左右が入れ替わることはあるが、初期値に戻るよりは
      設定し直す手間が少ない
    - 1 台から 2 台に増えた: 前と同じ端子の方は 1 で前の設定を使う。もう 1 台は、使われていない
      設定がないので 3 で新しいモニタになる
    - 2 台から 1 台に減った: 前と同じ端子なら 1 で使う。別の端子なら、使われていない 2 つの設定の
      うち、端子の番号順で先の方が 2 で割り当てられる
  - 組み合わせるのは「使われていない設定」だけなので、接続中の別のモニタが 1 で使っている設定を
    横取りすることはない。また、型番ごとに組み合わせるので、処理するモニタの順番で結果が変わらない
  - キーの形を変えないので、以前のバージョンの設定ファイルは移行の処理なしでそのまま読める
    (アップデート直後の起動は 1 で一致する)。FR-040 の引き継ぎを、別の処理を書かずに満たせる
  - 付け替えは設定を移すだけで複製しないので、同じモニタの設定が 2 つ並ぶことはない
    (spec.md の Clarifications で、古い ID を残す案を不採用にした理由と同じ)
  - 判定はすべて文字列の比較なので、Core の単体テストで場合ごとに押さえられる
- **Alternatives considered**:
  - キーを型番だけ (`SNYAE04`) や `型番#端子` の新しい形に変え、読み込み時に古いキーを移行する案
    (移行の処理が別に必要になる。また、型番だけのキーでは、1 台から 2 台に増えたときに「前と
    同じ端子の方」を決められないため不採用)
  - モニタの EDID を読み、シリアル番号で個体を見分ける案 (spec.md の Clarifications で不採用)
  - 付け替えずに、見つけた設定を新しいキーへ複製する案 (同じモニタの設定が 2 つ並び、端子を戻した
    ときに古い方が使われてしまうため不採用)
  - 2 で、接続中にその型番が 1 台だけで、その型番の設定も 1 つだけのときだけ移し、それ以外は新しい
    モニタにする案 (plan の初版で採っていた)。同じ型番の 2 台を引越しなどで別の端子につなぎ直すと
    2 台とも初期値に戻り、同じ型番の設定が一度 2 つになると以後ずっと引き継げなくなるため、上の
    組み合わせ方に置き換えた (`/speckit-analyze` の 3 回目の指摘 M1 と、その後の人間との相談)
  - 同じ型番どうしを、画面の並び (左・右) で見分けて割り当てる案 (各モニタの並びを設定ファイルに
    新しく保存する必要があり、小さな変更の範囲を超えるため不採用)

- **補足**: 以前のバージョンで端子を挿し替えたことがあると、挿し替えた先に初期値の設定が足されて
  いる。そのため 2 で、本来の設定ではなく、その初期値の設定が割り当てられることがある。その場合は
  利用者に設定し直してもらう (spec.md の Edge Cases)

  - 同時につないでいる `SNYAE04` と `DELF16C` は `UID4352` と `UID4353` で、出力先が違えば値も違う

- 未確認の前提が 2 つ残る。どちらも同じ型番のモニタ・EDID を読めないモニタが必要で、手元の環境では
  確かめられない。外れた場合の動きは今までと同じで、設定を失うことはない

## 21. 日付の区切り文字に任意の文字列を使う (FR-026、2026-09-28 追加、issue #60)

- **Decision**:
  - `DateSeparatorResolver.Resolve` は、`null` のときだけ「/」を返し、それ以外 (空欄・選択肢にない
    文字列を含む) はそのまま返す
  - 日付の文字列は、書式文字列に区切り文字を埋め込まず、年・月・日の数字と区切り文字をつなぎ合わせて
    作る。この処理を Core に `DateTextFormatter` として切り出し、単体テストで押さえる
    - 年は 4 桁、月・日は 2 桁で、今の表示 (`yyyy/MM/dd`) と同じ
  - 詳細設定画面の選択肢は「/」「-」「.」の 3 つにする。設定の区切り文字が選択肢にないときは、
    `ComboBox.SelectedItem` に明示的に `null` を入れて空欄にする
  - 空欄のまま画面を閉じたり、ほかの項目を変えたりしても、区切り文字は書き換えない
    - `SelectionChanged` は、初期化中は今までどおり `_isInitializing` で無視する
    - 利用者が選択肢を選んだときだけ、その値を保存する
  - 設定ファイルの書き出し方は変えない。英数字以外の区切り文字 (絵文字など) は、保存し直すと
    `\uXXXX` の形になるが、読み込めば同じ文字に戻る。このことを contracts/settings-file.md に書く
    (`/speckit-analyze` の指摘 E1、人間が決定)
- **Rationale**:
  - 今の実装は `now.ToString($"yyyy{separator}MM{separator}dd")` で、区切り文字を書式文字列に埋め込んでいる
    - そのため `y`・`M`・`d`・`'`・`\`・`%` などを区切り文字にすると、書式の記号として解釈される
    - 例: 区切り文字を `d` にすると、そこに日の数字が出る
    - FR-026 の「任意の文字列」を満たすには、書式文字列から切り離す必要がある (サブエージェントによる clarify の見直しの指摘)
  - エスケープして埋め込む方法よりも、つなぎ合わせる方が、どんな文字列でもそのまま出ることが分かりやすい
  - 書式文字列の `/` は、実行環境の地域設定の日付の区切りに置き換わる
    - 日本語環境では「/」なので、つなぎ合わせる形に変えても表示は変わらない (Assumptions の日本語環境の前提)
  - 選択肢にないときに `SelectedItem` へ値をそのまま入れる方法では、空欄にならない (下の確かめた結果の 2)
- **Alternatives considered**:
  - 区切り文字を `'...'` で囲んで書式文字列に埋め込む案
    - 区切り文字に `'` や `\` が含まれると、さらにエスケープが要る
    - どんな文字列でも正しく出ることを確かめにくいため不採用
  - 選択肢にない文字を、選択肢の末尾に足して選択中にする案 (specify の初版で採っていた)
    - issue #60 のコメントで、人間が空欄で表示すると決めていたため不採用
  - 書き出しの `Encoder` を `JavaScriptEncoder.UnsafeRelaxedJsonEscaping` にし、書いた文字のまま保存する案
    - 最小のコンソールアプリ (.NET 10) で確かめたところ、日本語 (`游ゴシック`) と `&` はそのまま書き出されたが、
      絵文字 (`🍣`) は `\uD83C\uDF63` のままだった。隠し機能の代表例である絵文字に効かないため不採用
    - 絵文字もそのまま書き出す `JavaScriptEncoder` を自作する案は、隠し機能のためには作り込みすぎのため不採用 (原則 I)
    - どちらの設定でも、`\uXXXX` の形・そのままの形のどちらのファイルも同じ値として読めることを、同じアプリで確かめた

## 22. 設定をモニタごとに持つときの設定ファイルの形と、以前の設定の引き継ぎ (FR-040, FR-041, SC-005、2026-10-01 追加、issue #53)

- **Decision**:
  - `MonitorPlacement` に `Appearance` (`AppearanceSettings`) と `WindowBehavior` (`WindowBehaviorSettings`) を持たせる
    - クラスの中身 (項目) は変えず、置き場所だけを 1 段下げる
    - 新しく作るエントリの値は、今の既定値 (`new()`) のまま。最前面表示 ON・位置ロック OFF
  - `WidgetSettings` の `Appearance`・`WindowBehavior` は、以前のバージョンの設定を読むためだけに残す
    - null を許す型にし、null のときは書き出さない (`JsonIgnore(Condition = WhenWritingNull)`)。JSON の名前は今と同じ
    - 設定ファイルのこの 2 つに値があれば、以前のバージョンの設定ファイルとみなす
  - 引き継ぎは `MonitorSettingsReconciler.Reconcile` の中で、FR-040 の付け替えの後、新しいモニタのエントリを足す前に 1 回だけ行う
    - 以前のバージョンの設定ファイルなら、`Monitors` のすべてのエントリに、全体の `Appearance`・`WindowBehavior` の複製を入れる
    - そのうち、キーが接続中のどのモニタとも一致しないエントリは、`IsVisible` を false にする (FR-041、spec.md の Clarifications)
    - 終わったら全体の 2 つを null にする。次の保存から書き出されなくなり、引き継ぎは二度と起きない
  - 新しいモニタ (FR-040 で割り当てるエントリがないモニタ) は、既定値で `IsVisible = false` のエントリを足す
    - ただし `Reconcile` を呼んだ時点で `Monitors` が空なら、プライマリモニタだけ `IsVisible = true` にする
    - プライマリモニタが見つからないときは、列挙した先頭のモニタを表示する (どこにも出ないのを避けるため)
  - 複製は `AppearanceSettings.Clone()`・`WindowBehaviorSettings.Clone()` で作る
    - 中身は値型と文字列だけなので、`MemberwiseClone` で足りる
    - 同じインスタンスを共有すると、あるモニタの変更がほかのモニタに伝わってしまう (SC-009)
- **Rationale**:
  - モニタごとの設定は、すでに `MonitorPlacement` が持っている (表示/非表示・位置)
    - 同じエントリに見た目も入れれば、FR-040 の付け替えと、取り外したモニタの設定を残す扱いが、そのまま見た目にも効く
    - 別の辞書 (`AppearanceByMonitor` など) に分けると、付け替えを 2 つの辞書で揃える処理が要る
  - 以前のバージョンかどうかは、全体の `Appearance` があるかで判定できる
    - 新しい形のファイルには書き出さないので、バージョン番号のフィールドを足さずに済む (contracts/settings-file.md の後方互換性)
    - モニタのエントリに `Appearance` がないことで判定する案だと、読み込んだ時点で初期値 (`new()`) が入ってしまい、見分けられない
  - 引き継ぎを `SettingsRepository.Load` でなく `Reconcile` で行うのは、つながっていないモニタを非表示にするのに、接続中のモニタの一覧が要るため
    - FR-040 の付け替えより後に行うのは、別の端子につなぎ直したモニタを「つながっている」と扱うため
  - 「起動時だけ判定する」(spec.md の FR-041) を、`Reconcile` を呼んだ時点で `Monitors` が空かどうか、で実装する
    - `Monitors` のエントリは消さない (取り外したモニタの設定も残す) ので、起動して 1 つでも足した後は、空に戻ることがない
    - なので、起動時だけ判定するのと同じ結果になる。起動時かどうかを `Reconcile` に渡す引数は要らない
- **Alternatives considered**:
  - 全体の `Appearance` を「新しいモニタのひな形」として残し続ける案
    - 新しいモニタは既定値で始めると決めたので (spec.md の Clarifications)、ひな形は要らない
  - 以前のバージョンへ戻したときのために、全体の `Appearance`・`WindowBehavior` も書き出し続ける案
    - 以前のバージョンへ戻すことへの対応は範囲外 (spec.md の Assumptions)。書き出し続けると、どちらが正しい値か分かりにくくなる
    - なお、新しい形のファイルを以前のバージョンで読むと、全体の `Appearance` がないので既定値の見た目で起動する。壊れたファイルの扱いにはならない
  - 設定ファイルにバージョン番号を足して判定する案
    - 判定に使うのはこの 1 回だけで、全体の `Appearance` の有無で足りる (原則 I)
- 保存時の `BackgroundOpacity` のクランプ (`SettingsRepository.Save`) も、ルートではなく各モニタの `Appearance` に対して行う
  - ルートの `Appearance` は引き継いだ後は null なので、今のままだと起動時の保存で落ちる (`/speckit-analyze` の指摘 C1)
- **確かめておく前提**: なし
  - `JsonIgnore(Condition = WhenWritingNull)` と、項目がないときに初期値が残る動きは System.Text.Json の挙動で、WPF の挙動ではない
  - どちらも実装の単体テスト (`SettingsRepositoryTests`) で押さえる

## 23. 詳細設定画面で編集するモニタを選ぶ (FR-013, FR-014, FR-042、2026-10-01 追加、issue #53・#17)

- **Decision**:
  - `SettingsWindow` の `TabControl` の上に「編集するモニター」の `ComboBox` を置く
    - 選択肢は接続中のモニタを番号順に並べ、ラベルは今のモニタ一覧と同じ「モニター N」「モニター N (プライマリ)」にする
    - 非表示のモニタには「(非表示)」を付ける。プライマリで非表示なら「(プライマリ、非表示)」
    - 選択肢は `Identifier` とラベルを持つ小さなクラスで表し、選んだモニタは `Identifier` で覚える
  - 「モニター・起動」タブはなくす
    - 「表示」タブの先頭に「このモニターに表示する」の `CheckBox` を置く (FR-014)
    - 自動起動の `CheckBox` は、タスクトレイの右クリックメニューに移す (#24)
  - モニタを選ぶと、全タブのコントロールに、そのモニタの `MonitorPlacement` の値を入れ直す
    - 入れ直している間は `_isInitializing` で各コントロールの変更イベントを無視する (下の前提 2)
    - 変更イベントは、選んだモニタの `MonitorPlacement` に書き込み、App へモニタの `Identifier` を付けて知らせる
    - App は、そのモニタのウィジェットにだけ見た目を反映し、保存する (非表示のモニタはウィジェットがないので、保存だけ)
  - 画面を開くときに選ぶモニタ (FR-042)
    - ウィジェットの右クリックメニューから開くときは、そのウィジェットのモニタの `Identifier` を App に渡す
    - タスクトレイから開くときは渡さず、プライマリモニタを選ぶ
    - すでに開いているときは、ウィジェットから開いたならそのモニタに切り替えてから前に出す。タスクトレイからなら、選択を変えずに前に出す
  - モニタの抜き差し (issue #17)
    - App の `OnDisplaySettingsChanged` で、`Reconcile` の後に、開いている `SettingsWindow` へ接続中のモニタの一覧を渡す
    - `SettingsWindow` は選択肢を作り直し、選んでいたモニタの `Identifier` があれば、それを選び直す
      - モニターの番号が振り直されても、同じモニタを選んだままにできる
    - なければ、プライマリモニタを選び、コントロールに値を入れ直す
      - FR-040 の付け替えで `Identifier` が変わった場合 (起動中に別の端子につなぎ直した場合) もこちらになる。普段の操作ではまず起きないので、気にしない
    - 「このモニターに表示する」を切り替えたときも、ラベルの「(非表示)」を変えるため、同じ処理で選択肢を作り直す
  - 選択肢を作り直すときは `_isInitializing` で `SelectionChanged` を無視し、作り直した後に `Identifier` で選び直す (下の前提 1)
- **Rationale**:
  - 選んだモニタの値を入れ直す形にすれば、各コントロールの変更イベントの処理は、書き込み先が変わるだけで今のまま使える
  - ラベルの「(非表示)」を変えるたびに選択肢を作り直す方が、選択肢のクラスに変更通知を付けるより単純 (原則 I)
- **Alternatives considered**:
  - モニタごとのタブにする案、ボタンを並べて切り替える案 (spec.md の Clarifications で不採用)
  - 選択肢を `record` にする案
    - 値が等しい選択肢が新しいリストにあると、選択が自動で残る (下の前提 1)
    - 作り直した後に必ず選び直すので結果は同じだが、動きが 2 通りになって分かりにくいため、参照で比べるクラスにする

### 前提としている WPF の挙動 (constitution Development Workflow 7)

| 前提 | 結果 | 根拠 |
|---|---|---|
| 1. `ComboBox.ItemsSource` を新しいリストに替えると、選択が外れ、その場で `SelectionChanged` が起きる。新しいリストの要素を `SelectedItem` に入れると選び直せる | 確認済み。ただし、新しいリストに `Equals` で等しい要素があると、選択が残り `SelectionChanged` も起きない | 下の確かめ方を参照。どちらの動きでも、無視してから選び直すので結果は同じ |
| 2. `CheckBox.IsChecked` をコードから変えると、`Checked`/`Unchecked` がその場で起きる。同じ値を入れたときは起きない | 確認済み | 同上。`Slider.Value` の `ValueChanged` も同じ (既存の `SettingsWindow` のコメントのとおり) |

- 確かめ方と結果 (2026-10-01)
  - scratchpad に最小の WPF アプリ (.NET 10、`ThemeMode = System`) を作り、コードから次の順に操作して、そのつど状態とイベントを記録した
    - `Identifier` とラベルを持つ `record` の 2 要素のリストを `ItemsSource` に入れ、2 つ目を選ぶ → `SelectionChanged` 1 回
    - ラベルだけ違う新しいリストに替える → `SelectionChanged` (外れた 1 つ) が起き、`SelectedItem` は null (前提 1)
    - 新しいリストの 2 つ目を `SelectedItem` に入れる → 選ばれ、`SelectionChanged` が起きる (前提 1)
    - 値の等しい `record` の新しいリストに替える → 選択が残り、`SelectionChanged` は起きない (前提 1 のただし書き)
    - 選択中の要素がない 1 要素のリストに替える → `SelectionChanged` が起き、`SelectedItem` は null
    - `CheckBox.IsChecked` を true → false にする → `Checked`・`Unchecked` が 1 回ずつ。もう一度 false を入れても起きない (前提 2)
    - `Slider.Value` に 40 を 2 回入れる → `ValueChanged` は 1 回 (前提 2)
  - 確認用のアプリは scratchpad に置いた一時的なもので、リポジトリには含めない
- 画面を開いたままモニタを抜き差しする操作は、実装後に quickstart.md の US4 の手順で実機で確かめる

## 24. タスクトレイの右クリックメニューを詳細設定・自動起動・終了だけにする (FR-019, FR-031, FR-038、2026-10-01 追加、issue #53)

- **Decision**:
  - トレイの右クリックメニューは「詳細設定...」「自動起動」(チェック付き)「終了」だけにする (contracts/context-menus.md)
    - 位置ロック・最前面表示・配置の項目と、モニタを選ぶ階層はなくす (この research.md の #17 の決定の取り下げ。issue #17 とは別)
    - 左クリックで全ウィジェットを前に出す動き (FR-031) は変えない
  - 「自動起動」を選ぶと、`AutoStartEnabled` を反転し、今の `OnAutoStartChanged` を呼ぶ
    - 切り替えに失敗したときに値を戻してメッセージを出す処理 (issue #18) は、そのまま使う
    - メニューは開くたびに作り直すので、失敗して値が戻っても、次に開いたときのチェックは正しい
  - スタートアップフォルダのショートカットを書き換えるのは、今までどおり、利用者が自動起動を切り替えたときだけにする (issue #20)
    - 起動時や詳細設定画面を開いたときには書き換えない
  - 本体の右クリックメニューの項目は変えない
    - 位置ロック・最前面表示は、そのウィジェットの `MonitorPlacement.WindowBehavior` を切り替え、そのウィジェットにだけ反映して保存する
    - 配置のサブメニューは、そのウィジェットの位置ロックでグレーアウトを決める
- **Rationale**:
  - 位置ロック・最前面表示・配置はモニタごとになったので、そのモニタのウィジェットのメニューで切り替えるのが分かりやすい (spec.md の Clarifications)
  - 自動起動はアプリ全体で 1 つの設定で、モニタを選んで設定する詳細設定画面には合わない
- **Alternatives considered**:
  - トレイのメニューに、位置ロック・最前面表示・配置それぞれのモニタの階層を付ける案、先にモニタを選ぶ案
    - spec.md の Clarifications で不採用。経緯は ui-per-monitor-settings.md のコミット `48a675a` の版にある
- **確かめておく前提**: なし (チェック付きの項目は、今のトレイのメニューの位置ロックと同じ作り方で、issue #34 で確かめている)
